# Implementation Plan

## Workflow

**inspect → reason → one bounded change → targeted verification → diff/review → commit → checkpoint**

One learning/build objective at a time. Evidence decides what comes next.

## Objective 0 — Current program inspection

Before application implementation:

- inspect current Challenges;
- inspect Infrastructure;
- inspect Ways to Earn XP;
- inspect Rewards;
- inspect Track Points;
- inspect FAQ and guidelines;
- verify current deadlines and submission requirements;
- record the first smallest justified technical objective.

Acceptance: repository requirements ledger reflects the current Academy contract rather than assumptions from ACT III or older event material.

## Objective 1 — AMD environment proof

Establish a reproducible AMD-backed execution environment and run the smallest meaningful workload.

Record exact GPU/runtime/framework facts, setup steps, quota/cost behavior, and observed friction.

Acceptance: genuine AMD execution is independently demonstrable.

## Objective 2 — Structured autonomous proposal

Run an AMD-backed AI workload that emits a bounded structured proposed action rather than directly performing a consequential action.

Acceptance: model capability is cleanly separated from execution.

## Objective 3 — UCII identity binding

Bind the autonomous actor to UCII through the public UCII boundary.

Acceptance: the workload can be attributed to a verified UCII identity without treating verification as authorization.

## Objective 4 — Fail-closed authority boundary

Require matching UCII authority before the deterministic executor accepts a consequential proposed action.

Acceptance: verified identity + capable model + no authority = DENY.

## Objective 5 — Bounded grant / execute / revoke proof

Demonstrate narrow human-granted authority, successful in-scope execution, revocation, and fresh denial after revocation.

Acceptance: same actor and capability produce different execution outcomes solely because authority state changed.

## Objective 6 — Provenance and judge evidence

Expose the sequence in a compact evidence surface that distinguishes identity, proposal, authority, decision, execution, and revocation.

## Objective 7 — Academy experiments and challenge participation

Use Academy mini-challenges and learning milestones when they genuinely improve AMD/ROCm competence or the UCII integration. Keep each experiment bounded and documented.

## Objective 8 — Adversarial validation

Test missing, expired, revoked, wrong-actor, wrong-scope, replay/stale, model-claims-authority, AMD-runtime-failure, and UCII-failure cases as applicable.

## Objective 9 — Final Academy submission

Select the strongest evidence-backed project shape produced during the program and package the final repository, presentation, video/demo, product feedback, and submission materials.

## Scope rule

Do not prematurely decide the final December project before current challenge mechanics and AMD infrastructure are inspected. The Academy is long enough for real evidence to improve the concept.
